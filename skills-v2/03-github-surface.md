# GitHub (powierzchnia pamięci publicznej)

## Rola
Publiczna **pamięć** projektu: konstytucja, historia decyzji, otwarte wątki — nie Twój warsztat na co dzień.

## To jest / To nie jest
| To jest | To nie jest |
|---------|-------------|
| Źródło prawdy tekstu i wersji | Miejsce, w którym „używasz lab’u” |
| Sygnał dojrzałości (release, issues) | Wymóg, byś reviewował każdy commit |
| Interfejs dla współpracowników | Interfejs filozoficzny dla end-usera |

## Błędy zakresu
1. **Czytanie diffów zamiast konstytucji / issues o sensie** — spadek w rzemiosło.  
2. **Mylenie „jest na GitHubie” z „jest publicznym labem do przejścia”** — to jeszcze nie Vercel/preview.  
3. **Otwieranie 20 technicznych issues**, gdy brakuje 1 decyzji konstytucyjnej.

## Błędy systemowego niezrozumienia
- Traktowanie liczby commitów jako postępu moralnego lab’u.  
- Myślenie, że issue „bug button” = issue „łamanie non-negotiable”.

## Zostań na górze, gdy…
- Pytasz: czy konstytucja i 10 tur są opisane? czy release jest oznaczony?  
- Priorytetyzujesz issues po **znaczeniu dla osi / pewności**, nie po stacku.

## Zejdź głębiej, gdy…
- Publiczny opis kłóci się z tym, co widzisz w labie.  
- Issues sugerują „poprawną odpowiedź moralną” jako feature.  
- Nie ma śladu decyzji, którą uważasz za zamkniętą (np. lock 10 tur).

## Pytanie kontrolne
*Czy GitHub właśnie trzyma **sens**, czy wciąga mnie w **warsztat, którego nie chcę prowadzić**?*
